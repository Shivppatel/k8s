# Sherlock deployment declaration

Private Sherlock images run through the existing app-template 5.3.0 wrapper. `values.yaml` is the source of truth for immutable service/runtime/egress image digests, source switches, model, daily budget and endpoint/secret references. The service pin is sherlock main 50337e6daab9bad47dd86b54eceac25844970cf8 (Go 1.27.3, [PR #27](https://github.com/Shivppatel/sherlock/pull/27)), published by [run 39560956608](https://github.com/Shivppatel/sherlock/actions/runs/39560956608). It includes the earlier reviewed query-profile work from [PR #21](https://github.com/Shivppatel/sherlock/pull/21). It prioritizes one exact configured alert Pod within the existing four workload reads and retains selected current/last/init-container status. Pod UID, creation and termination times identify current snapshot coverage; they do not establish an older episode or application ownership. It retains a distinct literal-only Kubernetes Service selector and a fourth Prometheus query for target scrape evidence, retaining explicit native Argo application bindings without inventing a Datadog service alias. It also retains bounded Alertmanager v0.34.1 routing metadata compatibility and source-correct timeline labels. Seven private scope profiles separate pod, workload, namespace, node, service-target, PVC (storage) and unknown alerts; the independently configured sender selects warning/critical namespace alerts across all namespaces after the reviewed consumer-readiness gate. Existing Alertmanager Slack remains the paging path while Sherlock adds bounded investigation updates. The runtime keeps its reviewed 2be4bbc442fa91c464fe7c6598a8e84cb2a45a70 pin from [source PR #16](https://github.com/Shivppatel/sherlock/pull/16). Egress keeps its existing 36b8433988345b04c57cf54f56f65a0f641338c3 digest. Runtime and source credentials are separate; the model receives bounded evidence from Go collectors and has no source access or infrastructure execution tools.

## Incident response and telemetry

The dashboard uses saved monitor/alert names, readable briefings and System/Light/Dark appearance. Compact Slack updates link to the full investigation. Alerts resolve only from their originating source's recovery; recovery is not proof of an RCA or application repair.

Each Datadog, Alertmanager, Prometheus, Loki, Tempo, Grafana and Pyroscope connection has an independent `enabled` switch under `sherlock.config`. Datadog-only, native Prometheus-stack-only and mixed installations are supported by the matching source release. [Observability configuration](observability/README.md) describes the exact endpoints, scope bindings, secret fields, transport and sender activation boundary.

Default Prometheus templates retain namespace restarts, the alert Pod's memory working set as a fraction of its limit, namespace container termination reasons (for example OOMKilled) and the Service scrape `up` series. Prometheus metrics, Loki logs, Tempo search matches and Pyroscope CPU/memory profile summaries are queried directly. Grafana supplies only the configured dashboard/panel definitions and links. Queries are operator-owned templates with literal scope placeholders; missing scope produces an explicit coverage gap. Current definitions/state, empty results and sampled profiles do not establish incident-time health or causality. Duplicate data across providers is not independent corroboration.

Kubernetes/Argo discovery uses validated namespace/workload UIDs and tracking ownership before repository fan-out. The GitHub App can read only the configured k8s and k8s-private repositories. tf/ and helm/ ownership appears in the editable context but does not grant additional source access. Datadog notebook retrieval is supported; no IDs are configured. No Kubernetes audit or retained Argo log source is configured.

The model is selected once at `sherlock.config.runtime.model`; runtime configuration derives that value. [AI context](ai/README.md) exposes the response prompt, installation AGENTS and telemetry/GitOps skills next to the app spec. Service and runtime must agree on the compiled profile digest. Editing context changes both ConfigMaps and requires a reviewed rollout; it does not change tools, credentials, source scope or budgets. No fresh semantic accuracy claim follows from adding connectors.

## Evidence and storms (sherlock#29–#31)

Every pod alert collects an identity-verified Pod snapshot and its events, follows UID-verified controller owner references in the same namespace to the owning workload and, when discovery verifies the Argo tracking ID, the Application and its GitOps history. Namespace-scoped alerts get a bounded sample of unhealthy Pods and Warning events; unschedulable Pods add a node summary. Each investigation carries `source_coverage`, `prior_incidents` and `concurrent_incidents`. Alert storms (`storm`: 5 incidents in 180s) post one Slack summary, delay collection up to 90s so peers are visible, fold findings into 10-minute digests and analyze at most 8 incidents per storm; the rest keep saved evidence. `SherlockEvidenceSourceAuthFailing` fires when a source returns 401/403. The operator context in `ai/` includes the shared-dependency map.

## Datadog metrics (sherlock#32–#33)

Datadog US5 supplies scoped metrics for native alerts (logs and traces stay in Loki/Tempo): per-namespace memory working set against limits, restarts, terminations by reason and CPU throttling (`metric_templates`); a `pvc` profile (72h) for the generated storage mappings; and the `shared-postgresql` dependency profile (7d: replication slot lag, WAL size, connection saturation, PVC usage) attached to incidents in authentik, coder, datadog, gitlab, immich, memos, n8n, postgresql, sherlock and teslamate. Templates are fixed; only validated literal tag values are substituted. Unmapped workload-scoped alerts collect the workload, its owner-verified Pods and the Deployment rollout state.

## Correlation (sherlock#35)

`concurrent_incidents` lists peers that alerted in the same window, incidents still open from up to 12h earlier (`correlation.ongoing_lookback_hours`, for slow cascades) and alerts received within 120s (redelivery bursts), each tagged with why it was included.

## Recent-change attribution (sherlock#39)

Each investigation carries a derived `recent_changes` observation: image tag/digest, chart version and resource changes parsed from the Application path's GitOps history, plus rollout image changes from Kubernetes snapshots, ordered by minutes before the incident. It makes no extra requests and is a candidate list, not proof of cause.

## Scrape-target health (sherlock#41)

Scrape-style alerts (TargetDown, TargetMissing, InstanceDown, Scrape* names) add a `prometheus_targets` observation from one fixed read of `/api/v1/targets?state=active`, filtered to the incident namespace and the alert's service, job and pod: health, redacted `last_error`, scrape age, duration and timeout for up to 12 targets. It is on by default; `target_health: false` on a Prometheus source disables it.

## Budget, feedback and persistence

The service allows 50 service-managed AI attempts per America/New_York calendar day across all workers/connections. Failures and retries consume durable permits. Raising the limit does not reset permits already used that day or replay terminal overflow reports. Overflow incidents retain evidence and an explicit unknown-cause limit report; they are not automatically analyzed tomorrow. This cap does not limit incident storage, source reads, Slack posts or account-wide use. Runtime limits remain one request, 120 seconds and 100 KB input; incident lookback is 15 minutes. There is no API-billed fallback.

[Authenticated feedback](feedback/README.md) uses the existing three-identity Homelab Lockdown human Allow list, a dedicated Access application/audience and backend signed identity verification. The public dashboard exposes no feedback rows or author fields. Assessments have an explicit retention hold, optional corrections are disabled, and no assessment automatically trains or changes the model. Owner UI-test ratings are not accuracy ground truth.

The service uses schema 6, introduced by the feedback release. This telemetry release adds no migration. Earlier schema-5 images cannot restart against schema 6; any recovery needs a reviewed compatible forward fix or Sherlock-only restore. Retention remains undecided and automatic cleanup disabled. A previously verified encrypted pre-migration Sherlock-only backup/key is held privately pending owner disposition; the recovery-key path must never be added to External Secrets access. No shared PostgreSQL backup is claimed.

Shared PostgreSQL role/bootstrap/database ownership and public CA mirroring remain in apps/postgresql. Sherlock runs its own migrations and verifies database TLS/hostname with the mirrored public certificate. The existing database, runtime, egress, reader scope, auth PVC and completed probe Jobs are preserved.

## Secret and network boundaries

Vault KV v2 under secret/Agents/sherlock supplies the existing Datadog/Slack, GitHub, database/public CA, runtime, registry and feedback fields through explicit ExternalSecrets. The new observability path supplies only the dedicated Grafana Viewer token and Alertmanager bearer. The exact observability read prerequisite in [Terraform PR #16](https://github.com/Shivppatel/tf/pull/16) was applied and merged before this consumer PR. The migration-backup key remains excluded. The Grafana administrator password is never mounted in Sherlock; an OSS Viewer credential has broader organization/data-source read/query rights than the collector's fixed dashboard GET allowlist.

Source, database, feedback and projected Kubernetes reader credentials mount only in the service. Runtime/auth pods use the retained dedicated Codex login PVC with a single writer and provider-proxy-only egress. Runtime/egress accounts have no reader bindings or automatic API tokens. Registry credentials are kubelet-only. The reader grants GET/LIST without Secrets, exec, logs or writes.

Connection-bound NetworkPolicy peers grant only service egress to the configured telemetry pods and Alertmanager ingress to the service. Disabling a connection removes its added peer grants. Private HTTP is explicitly opted into with exact Service-IP CIDRs; it is unencrypted inside the cluster. Grafana and Alertmanager bearer transport need that explicit review. Calico enforcement and actual positive/negative connectivity must be verified after an approved rollout; manifests alone are not isolation proof.

Public Traefik routes remain restricted to approved GET review paths, authenticated US5 Datadog intake and the separately protected feedback form. Alertmanager uses only the internal Service URL and its own bearer; no public Alertmanager route or Cloudflare exception is added. Model/config/admin/metrics/readiness routes stay private.
