# Sherlock deployment declaration

App-template 5.2.1 wrapper for the private Sherlock images published from source commit `36b8433988345b04c57cf54f56f65a0f641338c3`. All three images are pinned by verified immutable digest, contain AMD64/ARM64 manifests, and are pullable with the Vault-held read:packages credential. [Publication validation](https://github.com/Shivppatel/sherlock/actions/runs/38186192394) passed; this declaration has not yet been deployed.

Terraform prerequisites: [#13](https://github.com/Shivppatel/tf/pull/13) and [#14](https://github.com/Shivppatel/tf/pull/14) are applied and merged. Vault `secret/Agents/sherlock` supplies Datadog/Slack, while `secret/Agents/sherlock/webhook` supplies the inbound token through explicit field references. Registry fields in `secret/Agents/sherlock` feed only the kubelet image-pull Secret. GitHub signing key lives in `secret/Agents/sherlock/github`; database role credentials in `secret/Agents/sherlock/database`; public CA in `secret/Agents/sherlock/database-ca`; runtime API token in `secret/Agents/sherlock/runtime`. No values belong in Git.

`ExternalSecret/sherlock-db-secret` in `postgresql` supplies the CNPG managed role. The existing bootstrap/setup resources create only the Sherlock database/schema ownership. The prepared setup correction replaces repeated TeslaMate DROP EXTENSION CASCADE operations with CREATE EXTENSION IF NOT EXISTS and existing updates. A dependent table and row survived two runs in disposable PostgreSQL. Only Sherlock's public-schema defaults change. The app uses full database TLS/hostname verification and its own migrations. `PushSecret/sherlock-database-ca` mirrors only ca.crt into the dedicated public-certificate path; private key material is not mirrored or mounted by Sherlock.

In namespace sherlock, ExternalSecrets create sherlock-source-secret, sherlock-db-secret, sherlock-runtime-secret and sherlock-registry-secret. Source secrets/database/projected Kubernetes token mount only in the app. Its ServiceAccount binds the existing GET/LIST sherlock-reader ClusterRole with no new API scopes. Runtime/egress accounts have no bindings or automatic tokens. Registry credentials are not container mounts. NetworkPolicies require an enforcing CNI (Calico is present), and runtime/auth egress is DNS/provider-proxy only; actual packet denial must be verified after deployment.

The retained 1 GiB Longhorn PVC sherlock-codex-auth belongs only to the single-writer native runtime/auth phase. Initial runtime replicas are zero, runtime model calls are disabled, the device-login Job is enabled for the owner-approved fresh Kubernetes login, and ingress is disabled. The login Job requires zero runtime replicas at render time and stops after 15 minutes without retries. Its completed/failed object is retained while declared, preventing TTL/self-heal from creating repeated login attempts. Official device authentication is completed directly by the owner; Docker/desktop caches are not copied. A later reviewed activation disables the login Job and enables one runtime replica/model calls after successful login. Auth activation requires a positive structured report, not merely TCP readiness.

The prepared ingress is sherlock.shivpatel.xyz on Traefik websecure with only approved GET review routes and authenticated POST /webhooks/datadog/us5, bounded requests/rate and HTTPS headers. No public readiness, metrics, model, config/admin or mutation routes are declared. Existing wildcard TLS and actual hostname routing must be verified before enabling ingress. Incident retention remains undecided; no automatic cleanup is applied.

Definition of deployment completion: published immutable private image digests, registry access, all ExternalSecrets ready, exact Argo revisions/Synced/Healthy, database migrations/persistence, CA mirroring, provider credentials and network boundaries, scoped synthetic alert/ack/evidence/report/recovery, and public TLS/authentication boundary. Helm render/server dry-run does not establish any of those live outcomes.
