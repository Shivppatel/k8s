# Sherlock notification routing

`values.yaml` keeps the existing Alertmanager Slack/inhibition configuration as the source of truth. The optional `sherlockReceiver` block adds a separate authenticated internal receiver without modifying its definitions.

The committed route selects warning/critical alerts with a nonempty namespace across all namespaces. Existing silences/inhibition apply and Watchdog retains its null route. Each eligible alert reaches one Sherlock scope profile and the existing canonical Slack receiver. The unique synthetic marker retains a dedicated child without any generating rule. Node-only alerts without namespaces remain outside this filter.

`enabled` switches the Sherlock branch. `matchers` select its eligibility. `mirrorToExistingSlack` determines whether matching alerts also reach the original Slack route; it is true for this real-alert pilot. Omitted `routeTiming` keys inherit the existing policy. Full-label grouping keeps separate native alert episodes; the original Watchdog null route and inhibition rules remain in force.

Optional `profiles` are ordered child routes sharing the parent URL's exact scheme/host, native intake path pattern and existing bearer file. Every entry needs a unique `sherlock-` name, nonempty matchers and a compatible enabled Sherlock consumer. At most twelve children are accepted. Credentials, fragments, query strings, arbitrary paths and cross-origin destinations are rejected. Each child stops after its first match; the parent handles unmatched alerts. These are evidence-scope profiles within one trusted Alertmanager boundary, not independent authentication roles.

A future broad activation must first deploy and verify the compatible Sherlock image/configuration, then change only the generated Alertmanager configuration. Reversing that order sends notifications to missing consumers. Public Git publication, real-data exposure and continuing forwarding require the reviewed activation decision. Forwarding remains enabled after the initial observation; 50 AI attempts/New York day limits model use, not incident/evidence/Slack volume. Reports/evidence retention is undecided with cleanup disabled. A route-only pause restores the reviewed test-only matcher and empty profiles without disabling the receiver flag or removing credential mounts; it also stops real recovery delivery, so Sherlock can retain open incidents until source state is verified. Existing Slack remains the canonical paging path; Sherlock provides additional investigation messages in its test channel. The 50-attempt model budget does not bound incident count, evidence reads or Slack volume.

See [Sherlock observability configuration](../sherlock/observability/README.md) for source switches, profile bindings, credential references, retention limits and deployment boundaries.

`sherlockReceiver.profiles` currently has seven children (limit twelve). `sherlock-pvc` (`persistentvolumeclaim!=""`) is ordered before the node, pod and workload profiles so storage alerts reach `homelab-pvc-alerts`. `templates/sherlock-rules.yaml` adds the Sherlock self-observability `PrometheusRule`, which Prometheus selects through its `release: kube-prometheus-stack` label.

Custom rules in `templates/homelab-observability-rules.yaml` must keep a `namespace` label, or they reach Slack only. Collector and ingest alerts aggregate `by (namespace)` from their scrape (Alloy/Loki/Pyroscope in `observability`, Tempo in `tempo-distributed`). `ArgoAppDegraded` copies `dest_namespace`. `LonghornVolumeDegraded` copies `pvc_namespace`/`pvc` into `namespace`/`persistentvolumeclaim` for `sherlock-pvc` and ignores detached volumes, which Longhorn reports as robustness `unknown`. `NodeDiskPressure` keeps the kube-state-metrics `job`/`namespace` and matches `sherlock-node`. `ArgoAppOutOfSync` is deliberately not routed (routine during syncs).
